# Requirements Document

## Introduction

Risk Intelligence is Phase 1 of the RukPay post-MVP roadmap (GitHub issue #1). It combines four roadmap issues in one spec, because they share one data path, a payment evaluation, and they ship together:

- **#2 Explainable risk scores.** Every risk score lists the signals that added points, how many, and a calm sentence for each. #2 blocks the other three.
- **#3 Custom transaction input and fraud scenario builder.** A person enters their own payment details or fills them from a named fraud scenario, and sees the explained score. Depends on #2.
- **#4 Behavioural risk detection.** Extra capped points for payment speed, repeat attempts and departure from the payer's recent pattern, on top of the existing deterministic rules. Depends on #2.
- **#5 Trusted beneficiary management.** A payer keeps a list of recipients, new recipients get extra checks, and trust is earned slowly. Depends on #2.

The feature extends shipped code in `backend/internal/risk`, `store`, `vault`, `httpapi` and in `frontend/src`. It builds on three finished specs: `behavioral-risk-engine`, `cooling-off-vault` and `dual-screen-simulator`. The deterministic rules of `behavioral-risk-engine` stay the baseline. The vault state machine, the 900-second lock, the guardian flow, the anti-panic copy and the privacy rules stay as they are.

This feature extends these earlier requirements, and every other earlier requirement stays in force:

- `cooling-off-vault` 1.1 (evaluate), 7.1 (vault read fields), 10.1 (the six routes) and 10.7 (CORS methods) gain new fields, routes and methods.
- `dual-screen-simulator` 12.5 (what the Simulator may send) gains the new request fields named in Requirement 22. Requirement 2.1 (exactly three presets), Requirement 1 (dual-screen layout) and Requirement 12.4 (no control asks for an OTP, PIN or password) stay unchanged.
- `behavioral-risk-engine` 2.8 (same signals, same score) still holds for Signals alone. With history or a recipient, the score depends only on explicit arguments, as Requirement 9 states. `behavioral-risk-engine` 7.1 (`VaultStore` has exactly three methods) stays unchanged, and new storage uses new interfaces.

### Decisions fixed for this feature

1. **Who is "the payer" in Phase 1.** There are no accounts yet. History (#4) and recipients (#5) belong to one fixed demo payer on the server, named by one constant, Payer_Key. The browser holds no identifier. This is the safest and simplest option for four reasons. First, nothing in the browser can be stolen, guessed or leaked, and the smoke checks that forbid browser storage keep passing. Second, request bodies stay exactly as today, so existing clients and the three Presets are untouched. Third, a client-chosen profile id would act as a bearer secret that lets any caller read or change another profile, and it would be lost on every page load because the browser may not store it. Fourth, #6 replaces only the one constant with an account id. The cost is that every visitor of one deployment shares one history and one recipient list. Requirement 9 limits the effect on the Presets, and stored items expire. Real identity arrives with #6.
2. **Explanations are stored.** Signals are not stored today, so the Explanation is stored on the Vault_Record at creation and is not recomputed. It holds fixed sentences and no identifier.
3. **Added points only add.** Behavioural points and care points only increase a score and are capped. Trust never subtracts points from the baseline. A trusted recipient only adds no care points.
4. **Degrade to today.** If the history or the recipient list cannot be read, the evaluation continues with the baseline rules and the explicit request values, which is today's protection.
5. **Simulation boundary.** RukPay simulates payment decisions. Nothing this feature adds may describe a simulated approval, hold or cancellation as a real bank outcome. Some copy in the shipped screens, such as the payment-sent and cancelled messages, predates this boundary and is outside this feature.

## Glossary

- **Risk_Engine**: The Go package `backend/internal/risk`. It stays free of I/O and reads no clock.
- **Signals**: The five scoring inputs defined in `behavioral-risk-engine`.
- **Risk_Score**: The integer from 0 to 100 that the Risk_Engine returns.
- **Initial_State**: INSTANT_PASS, REALITY_CHECK or LOCKED_15M, mapped from the Risk_Score with the thresholds 40 and 75.
- **Baseline_Points**: The points that the five Signals earn under the tier rules of `behavioral-risk-engine` Requirement 2. The sum is at most 100.
- **Signal_Id**: A lowercase snake-case name for one source of points. Baseline: `amount`, `beneficiary_age`, `late_night`, `unknown_call`, `rapid_retries`. Behavioural: `velocity`, `daily_frequency`, `repeat_attempts`, `amount_deviation` and `pattern_<pattern id>`. Adjustments: `beneficiary_care`, `behaviour_cap`, `score_cap`.
- **Contribution**: One entry of an Explanation, with the JSON keys `signal` (a Signal_Id), `points` (an integer) and `reason` (one sentence).
- **Explanation**: The ordered list of Contributions of one evaluation. The JSON field name is `explanation`.
- **Behaviour_Points**: The sum of the behavioural Contributions after the Behaviour_Cap.
- **Behaviour_Cap**: 25 points.
- **Care_Points**: The points for a named recipient that is not on standard protection, defined in Requirement 18.
- **Care_Cap**: 10 points.
- **Payer_Key**: The one constant that names the Demo_Payer in every stored item.
- **Demo_Payer**: The single payer that owns all history and all recipients in Phase 1.
- **History_Event**: A stored record of one evaluation: time in epoch seconds, `amount_inr`, and the Beneficiary_Ref, which may be empty.
- **Beneficiary_Ref**: The Masked_Identifier of the recipient of a payment, or empty when the payment names no recipient.
- **History_Snapshot**: The History_Events of the Demo_Payer that were recorded before the current evaluation and are still within History_Retention, at most the 100 most recent.
- **History_Retention**: 7 days (604,800 seconds).
- **Within_Window**: A History_Event is within a window of W seconds when the evaluation time minus the event time is less than W. An event time later than the evaluation time counts as within every window.
- **Velocity_Window**: 600 seconds. **Frequency_Window**: 86,400 seconds. **Repeat_Window**: 3,600 seconds.
- **Fraud_Pattern**: One entry of the Pattern_Table, held as data: `id`, window in seconds, minimum count of small payments, small-payment maximum in rupees, large-payment minimum in rupees, `points` and `reason`.
- **Pattern_Table**: The ordered list of Fraud_Patterns.
- **Large_Payment_Threshold**: 10,000 rupees.
- **Beneficiary**: A recipient saved by the Demo_Payer.
- **Beneficiary_Id**: An opaque id of 32 lowercase hexadecimal characters from `crypto/rand`.
- **Beneficiary_Record**: The stored item for one Beneficiary: id, label, Masked_Identifier, added time, verified time, Trust_Level, Protection_Level, Pressure_Flag, version, payment count, first payment amount, History_Entries, `expires_at`.
- **Beneficiary_View**: The JSON projection of a Beneficiary_Record returned by the API.
- **Trust_Level**: `NEW` (not trusted yet) or `TRUSTED`.
- **Protection_Level**: `EXTRA_CARE` or `STANDARD`.
- **Pressure_Context**: A request in which `is_late_night` is true or `active_unknown_call` is true.
- **Pressure_Flag**: A boolean on a Beneficiary_Record. It is set when the Beneficiary is added in a Pressure_Context and when a Beneficiary_Verification is not passed. It is never cleared.
- **Trust_Waiting_Period**: 72 hours from the added time, or 168 hours when the Pressure_Flag is set.
- **Beneficiary_Verification**: The three calm questions asked about a new Beneficiary: `coercion`, `acquaintance` and `secrecy`.
- **Risk_Indicator**: A stable code on a Beneficiary_View: `ADDED_RECENTLY`, `ADDED_UNDER_PRESSURE`, `NOT_VERIFIED`, `WAITING_PERIOD`, `FIRST_PAYMENT_LARGE`, `EXTRA_CARE_ON`.
- **History_Entry**: One line in a Beneficiary_Record history: `at` in epoch seconds, a `kind` and, for a payment, `amount_inr`.
- **Avoid_Words**: The Banned_Terms of `dual-screen-simulator` plus `velocity`, `anomaly`, `heuristic`, `deviation`, `suspicious`, `fraud`, `fraudulent`, `criminal`, `dangerous`, `illegal`, `scammer`, `huge`, `massive`, `enormous`, `urgent`, `warning`, `alert` and `threat`, compared without regard to letter case.
- **Explanation_Card**: The block on the payer's phone that lists the Contributions of the current vault.
- **Guardian_Summary**: The short list of Contributions on the guardian's phone.
- **Scenario_Builder**: The in-phone form for custom payment details. It is the component `ScenarioBuilder.tsx`.
- **Fraud_Scenario**: A named one-click fill of the Scenario_Builder: Digital_Arrest, Courier_Customs or KYC_Expiry.
- **Demo_Contact**: A built-in recipient in the browser with a plain label, a Masked_Identifier and a default age in hours.
- **Beneficiary_Manager**: The in-phone screen for saved recipients. It is the component `BeneficiaryManager.tsx`.
- **Simulation_Notice**: A persistent sentence stating that RukPay simulates payment decisions and makes, holds or cancels no real payment.
- **Phone_Navigation**: The in-phone control that switches the User_Phone_Panel between Pay, Custom payment and Saved recipients.
- **Vault_Record**, **Vault_View**, **Vault_State**, **VaultStore**, **MemoryStore**, **DynamoDBStore**, **Fake_DynamoDB_Client**, **Masked_Identifier**, **Router**, **Vault_Service**, **Demo_Mode**: As defined in `behavioral-risk-engine` and `cooling-off-vault`.
- **Simulator**, **User_Phone_Panel**, **Guardian_Phone_Panel**, **Preset**, **Preset_Bar**, **API_Client**, **Privacy_Masker**, **Reality_Check_Modal**, **Banned_Terms**: As defined in `dual-screen-simulator`.
- **PBT_Suite**: The property-based tests written with `pgregory.net/rapid` (backend) or `fast-check` (frontend).

## Requirements

### Part A: Explainable risk scores (#2)

### Requirement 1: Per-Signal Contributions

**User Story:** As a payer, I want every score to list the signals that added points, so that I can see why RukPay paused or passed my payment.

#### Acceptance Criteria

1. WHEN the Risk_Engine scores a valid evaluation, THE Risk_Engine SHALL return an Explanation that holds exactly one Contribution for each Signal_Id other than `behaviour_cap` and `score_cap` that added more than 0 points, and no Contribution for any Signal_Id that added 0 points. A valid evaluation is one whose Signals have `amount_inr` greater than 0, `beneficiary_age_hours` of 0 or more, and `rapid_retry_count` of 0 or more.
2. THE Risk_Engine SHALL give every Contribution a `signal` from the Signal_Id list, an integer `points`, and a `reason` that has at least 1 character that is not whitespace and that follows the wording rules of Requirement 3.
3. THE Risk_Engine SHALL order the Contributions as follows, leaving out each Signal_Id that has no Contribution and listing no Signal_Id twice, whatever the size of its `points`: `amount`, `beneficiary_age`, `late_night`, `unknown_call`, `rapid_retries`, `velocity`, `daily_frequency`, `repeat_attempts`, `amount_deviation`, the pattern Contributions in Pattern_Table order, `behaviour_cap`, `beneficiary_care`, `score_cap`.
4. THE Risk_Engine SHALL return Contributions whose `points`, added as signed integers with the negative `behaviour_cap` and `score_cap` values included, equal the Risk_Score for every valid evaluation.
5. WHEN the sum of the `points` of the `velocity`, `daily_frequency`, `repeat_attempts`, `amount_deviation` and `pattern_<pattern id>` Contributions is greater than the Behaviour_Cap of 25, THE Risk_Engine SHALL add a `behaviour_cap` Contribution whose `points` equal 25 minus that sum, so that the behavioural Contributions and the `behaviour_cap` Contribution together add up to 25. For example, a sum of 30 gives a `behaviour_cap` Contribution of -5.
6. WHEN the sum of the Baseline_Points, the Behaviour_Points and the Care_Points is greater than 100, THE Risk_Engine SHALL add a `score_cap` Contribution whose `points` equal 100 minus that sum. For example, a sum of 108 gives a `score_cap` Contribution of -8.
7. WHEN no Signal_Id adds more than 0 points, so that the Risk_Score is 0, THE Risk_Engine SHALL return an Explanation that is an empty list with 0 Contributions. The Explanation SHALL be a present value and not an absent one, and SHALL be written in JSON as an empty array.
8. THE Risk_Engine SHALL return identical Explanations for the same Signals, the same History_Snapshot, the same evaluation time and the same recipient data. Identical Explanations have the same Contributions in the same order, with the same `signal`, `points` and `reason` in each.
9. THE Risk_Engine SHALL give the `amount`, `beneficiary_age`, `late_night`, `unknown_call` and `rapid_retries` Contributions the same `points` that `behavioral-risk-engine` Requirement 2 criteria 2, 3, 4, 5 and 6 give the same Signals, so that these five Contributions add up to the Baseline_Points.
10. THE Risk_Engine SHALL give every Contribution other than `behaviour_cap` and `score_cap` a `points` value greater than 0, and SHALL give a `behaviour_cap` or `score_cap` Contribution a `points` value less than 0.
11. IF the Signals fail validation under `behavioral-risk-engine` Requirement 1, THEN THE Risk_Engine SHALL return that validation error and no Explanation.
12. THE Risk_Engine SHALL add a `behaviour_cap` Contribution only as criterion 5 requires and a `score_cap` Contribution only as criterion 6 requires, so that a behavioural sum of exactly 25 or a total of exactly 100 adds no cap Contribution.

### Requirement 2: Explanation in Responses, Stream and Storage

**User Story:** As a client developer, I want the explanation in every vault response, so that both phones can show it and old clients keep working.

#### Acceptance Criteria

1. WHEN `POST /api/v1/transactions/evaluate` returns a Vault_View for a newly created vault, THE Router SHALL add to that Vault_View a field `explanation`. The field SHALL be a JSON array that holds the Contributions of that evaluation in the order in which the Risk_Engine returned them, and SHALL be the empty array `[]` when the Explanation is empty.
2. WHEN `GET /api/v1/vault/{id}` or `GET /api/v1/events/stream` returns a Vault_View of a vault that has a stored Explanation, including an empty one, THE Router SHALL include in that Vault_View an `explanation` field that equals the stored Explanation in Contribution count, order and the `signal`, `points` and `reason` values of each Contribution. An empty stored Explanation SHALL be written as `[]`. This SHALL hold for every Vault_View that the stream sends.
3. WHEN the Vault_Service creates a vault, THE Vault_Service SHALL store the Explanation of that evaluation on the Vault_Record in the same store write that creates the vault, so that no vault created after this feature exists without a stored Explanation (which may be empty). THE Vault_Service SHALL return the stored Explanation on every later read without recomputing it, so that a read made after the history, the recipient list or the Pattern_Table content would give a different result still returns the Contributions computed at creation.
4. THE MemoryStore and THE DynamoDBStore SHALL persist the Explanation as a new Vault_Record attribute and SHALL return it unchanged, with the same Contributions in the same order and equal `signal`, `points` and `reason` values. An empty Explanation SHALL read back as present with 0 Contributions. A Vault_Record stored without an Explanation, including a DynamoDBStore item that lacks the attribute, SHALL read back with no Explanation.
5. WHEN the Router returns a Vault_View of a Vault_Record that has no Explanation because it was written before this feature, THE Router SHALL omit the `explanation` key from the JSON (neither `null` nor `[]`), SHALL NOT compute an Explanation for it, and SHALL return every other Vault_View field equal to what the Router returned for the same Vault_Record before this feature.
6. THE Router SHALL keep every Vault_View field that existed before this feature, in the evaluate response, in the vault read response and in every stream event, with the same name, JSON type and meaning.
7. WHEN a vault changes Vault_State after creation, whether by a reality-check answer, a guardian action, a demo fast-forward or the 900-second expiry, THE Vault_Service SHALL keep the stored Explanation (an absent Explanation stays absent) and the Risk_Score unchanged, so that every later Vault_View shows the same `explanation` and the same `risk_score` as at creation.
8. THE Router SHALL return, in every Vault_View that holds an `explanation`, an `explanation` whose integer `points` values add up to the `risk_score` of the same Vault_View. The `behaviour_cap` and `score_cap` Contributions SHALL count with their negative values, and an empty `explanation` SHALL add up to 0.
9. THE Router SHALL write each Contribution in JSON as an object with exactly the keys `signal`, `points` and `reason` and no other key. `signal` SHALL be a JSON string, `points` SHALL be a JSON number with no fraction and not a string, and `reason` SHALL be a non-empty JSON string.
10. THE Vault_Service SHALL keep every identifier, every amount taken from the request and every reality-check answer text out of a stored Explanation, in every field including each `reason`. An identifier means a Beneficiary_Ref, a Masked_Identifier, a Beneficiary_Id, an account number, a UPI ID or a phone number.
11. IF the evaluate request is rejected, or the VaultStore cannot persist the new Vault_Record, THEN THE Router SHALL return the error response that it returned for that failure before this feature, with no Vault_View and no `explanation` field.
12. WHEN a request body sent to any route contains a field named `explanation`, THE Router SHALL treat that field as it treats any other unknown field before this feature and SHALL NOT store it or return it, so that every Explanation comes only from the Risk_Engine result of the evaluation.

### Requirement 3: Calm Explanation Wording

**User Story:** As a payer under stress, I want each reason in calm plain words, so that the explanation helps me think and does not alarm me.

#### Acceptance Criteria

1. THE Risk_Engine SHALL choose each `reason` as a fixed sentence selected only by the Signal_Id and the tier, where the tier is the `points` value that the rule of that Signal_Id awards, and where `behaviour_cap` and `score_cap` each have one sentence whatever their `points`, so that the same Signal_Id and tier always produce a byte-for-byte identical `reason` for every amount, count, time, History_Snapshot and recipient.
2. THE Risk_Engine SHALL write each `reason` as exactly one sentence of 1 to 20 words in everyday English, where a word is a run of non-space characters (so `15-minute` is one word), the sentence starts with an uppercase letter and ends with a single `.`, contains no other `.`, `!`, `?`, `…` or line break, and contains no run of more than 12 consecutive letters.
3. THE Risk_Engine SHALL write each `reason` without any of the Avoid_Words, where an Avoid_Word is found when it occurs anywhere in the `reason` as a substring compared without regard to letter case, so that `alerting` and `fraudster` are rejected as well.
4. THE Risk_Engine SHALL write each `reason` without a digit run longer than 4 digits (a digit run is consecutive ASCII digits 0 to 9), without the character `@`, without the text `[REDACTED]`, and without any text in a Masked_Identifier format, which means no `XXXX-XXXX-` followed by 4 digits and no `+91-XXXXXX` followed by 4 digits, compared without regard to letter case.
5. THE Risk_Engine SHALL describe the amount in each `reason` in words only and with no rupee figure, which means a `reason` contains no `₹`, none of the whole words `Rs`, `INR`, `rupee`, `rupees`, `lakh`, `lakhs`, `crore`, `crores`, `thousand`, `hundred` and `million` compared without regard to letter case, no digit run equal to 1000, 2000, 10000 or 25000, and no digit that is next to a `,` or `.` which is followed by another digit.
6. THE Risk_Engine SHALL return each `reason` such that `redact.Text` applied to it returns a string byte-for-byte equal to that `reason`.
7. THE Risk_Engine SHALL keep every explanation sentence, meaning every sentence that can be returned as a `reason` other than a Fraud_Pattern `reason`, as a named Go string constant in one source file of the Risk_Engine package that declares no other string constant, SHALL keep every Fraud_Pattern `reason` in the Pattern_Table, and SHALL build no `reason` at run time by formatting, concatenation or insertion of a value, so that one test checks every string constant of that file and every Fraud_Pattern of the Pattern_Table against criteria 2 to 6, fails when it finds no explanation constant, and checks a sentence added later without a change to the test.
8. WHEN the Vault_Service creates a vault in REALITY_CHECK or LOCKED_15M and the Explanation holds a Contribution with more than 0 `points` whose `signal` is `velocity`, `daily_frequency`, `repeat_attempts`, `amount_deviation`, `beneficiary_care` or `pattern_<pattern id>` (a behavioural or care Contribution), THE Vault_Service SHALL add to the vault `reason` summary sentence one plain phrase of at most 8 words, selected by the `signal` alone, for each such Contribution, placed after the reasons that the sentence already names, in Explanation order, and joined in the existing form of one phrase, two phrases joined by "and", or comma-separated phrases with "and" before the last.
9. WHEN the Explanation holds neither a behavioural Contribution nor a care Contribution, THE Vault_Service SHALL produce a vault `reason` summary sentence that is byte-for-byte equal to the sentence produced before this feature for the same Vault_State and the same Signals.
10. THE Vault_Service SHALL write each added summary phrase so that it meets criteria 3 to 6, SHALL add no phrase for `behaviour_cap`, for `score_cap`, for a baseline Contribution or for a Signal_Id that has no Contribution in the Explanation, and SHALL keep each added summary phrase as a named constant that a test checks without a change to the test when a phrase is added.
11. THE Vault_Service SHALL keep the vault `reason` byte-for-byte equal to the sentence produced before this feature for a vault created in INSTANT_PASS and for every `reason` written after creation, whatever the Explanation holds.

### Requirement 4: Explanation Card and Guardian Summary

**User Story:** As a payer and as a family guardian, I want to see why the payment was scored the way it was, so that the pause makes sense to me.

#### Acceptance Criteria

1. WHEN a Vault_View arrives in an evaluate response, a vault read or a stream event, and its `explanation` holds at least one Contribution, THE User_Phone_Panel SHALL show the Explanation_Card with one line for each Contribution, in the order of the list received, each line holding the `reason` and the points text of criterion 9. The Explanation_Card SHALL end with a total line that states the `risk_score` of the same Vault_View as a whole number followed by the word "point" or "points". The Explanation_Card SHALL NOT show any `signal` value as text.
2. WHEN a Vault_View arrives whose `explanation` is present and holds zero Contributions, THE Explanation_Card SHALL show one fixed sentence of at most 20 words, without any of the Avoid_Words, saying that nothing about the payment asked for extra care. The Explanation_Card SHALL show no Contribution line and no total line.
3. WHEN a Vault_View arrives with no `explanation` field, or with an `explanation` that is not a list whose every item has a string `signal`, an integer `points` and a non-empty string `reason`, THE User_Phone_Panel SHALL show no Explanation_Card, THE Guardian_Phone_Panel SHALL show no Guardian_Summary, and neither panel SHALL show an error. Every other part of both panels SHALL stay as it is without an `explanation`.
4. WHEN the `explanation` holds a `behaviour_cap` or `score_cap` Contribution, THE Explanation_Card SHALL show each such Contribution as its own line, in the position received, with its `reason` and its negative points text, and SHALL NOT merge it into another line.
5. THE Explanation_Card SHALL show each `reason` and each `points` integer exactly as the backend sent them, with no points computed, summed, rounded or changed in the browser. The only text the browser adds to a `points` integer is the sign and the word of criterion 9. THE Explanation_Card SHALL show each `reason` as plain text, so that markup characters in it appear as received and are never read as HTML.
6. WHILE the Pay screen is shown and the User_Phone_Panel holds a Vault_View with a usable `explanation`, THE User_Phone_Panel SHALL show the Explanation_Card readable without a tap or toggle. No timer or toast SHALL hide it. It SHALL stay through every Vault_State change of that vault. It SHALL be removed only when the Simulator discards that vault or replaces it with the vault of a new scenario, which starts when a Preset is pressed or "Simulate" is pressed.
7. WHILE the Vault_State is LOCKED_15M, THE Guardian_Phone_Panel SHALL show a Guardian_Summary that holds the `reason` and the points text of each of at most 3 Contributions taken from those with `points` greater than 0, ordered by `points` from highest to lowest, with equal `points` in the order of Requirement 1 criterion 3. WHEN more than 3 Contributions qualify, THE Guardian_Summary SHALL hold the first 3 in that ordering.
8. THE Guardian_Summary SHALL contain no `signal` value, no Masked_Identifier and no raw account number, UPI ID or phone number, and SHALL be shown in no Vault_State other than LOCKED_15M. THE Guardian_Phone_Panel SHALL keep the existing reason, amount, masked recipient, countdown and two action buttons displayed with the same content, and the two action buttons SHALL keep their labels, order and behaviour.
9. THE Explanation_Card and THE Guardian_Summary SHALL state the points of each Contribution as visible text made of a sign ("+" or "-"), the whole number, and the word "point" when the number is 1 or "points" otherwise, for example "+20 points" and "-5 points". They SHALL NOT convey the points by color or by an icon alone, and SHALL keep that text readable by assistive technology.

### Part B: Custom transaction input and fraud scenario builder (#3)

### Requirement 5: Custom Payment Form and Validation

**User Story:** As a person trying RukPay, I want to enter my own payment details, so that I can see how RukPay would treat a payment that is not one of the three Presets.

#### Acceptance Criteria

1. THE Scenario_Builder SHALL provide a labelled field for the amount in rupees, a recipient chooser, a labelled field for the hours since the recipient was added, a labelled switch for an active unknown call, a labelled switch for late night, a labelled field for the retry count, and a "Simulate" button.
2. WHEN the user presses "Simulate" and the amount, read under criterion 11, is not a whole number from 1 to 9,007,199,254,740,991, THE Scenario_Builder SHALL show a calm message (criterion 12) beside the amount field, SHALL send no request, SHALL keep every entered value, and SHALL leave the current vault unchanged.
3. WHEN the user presses "Simulate" and the hours since the recipient was added or the retry count, read under criterion 11, is not a whole number from 0 to 9,007,199,254,740,991, THE Scenario_Builder SHALL show a calm message (criterion 12) beside each such field, together with the message of criterion 2 when the amount is also not valid, SHALL send no request, SHALL keep every entered value, and SHALL leave the current vault unchanged.
4. WHILE a validation message is shown, THE Scenario_Builder SHALL keep it on screen, with no timer and no automatic dismissal, until the first of these events: (a) the user edits the field beside the message and the new value passes the rule for that field in criterion 2 or 3, or, for a message shown under criterion 7, the user changes the value of that field to any value; (b) the user presses a Preset button, presses a Fraud_Scenario button, or presses "Simulate" with every value valid. A message shown above the "Simulate" button under criterion 7 ends on a change to any field, switch or the recipient chooser, instead of event (a).
5. WHILE a validation message is shown beside a field, THE Scenario_Builder SHALL include the `id` of the element that holds that message in the `aria-describedby` of that field and SHALL set `aria-invalid` to `true` on that field, and SHALL remove both in the same update that removes the message.
6. THE Scenario_Builder SHALL apply no client-side rule beyond the backend rules, which are an amount above 0, an age of 0 or more and a retry count of 0 or more, and the upper bound of 9,007,199,254,740,991 in criteria 2 and 3, so that criteria 2 and 3 are the only reasons for which "Simulate" sends no request on account of the values, and every other rule is left to the server.
7. IF the server answers HTTP 400 with an error body that carries a `message`, THEN THE Scenario_Builder SHALL show that `message` unchanged beside the amount field when `field` is `amount_inr`, beside the hours field when `field` is `beneficiary_age_hours`, beside the retry count field when `field` is `rapid_retry_count`, and above the "Simulate" button when `field` is absent or has any other value, SHALL keep every entered value, and SHALL enable the buttons again.
8. THE Scenario_Builder SHALL set `inputmode="numeric"` on the amount, hours and retry count fields, and SHALL set `autocomplete="off"` on each of those three fields.
9. THE Scenario_Builder SHALL show a visible label for the amount, hours and retry count fields, for each of the two switches and for the recipient chooser, SHALL tie each label to its control so that the label is the accessible name of the control, and SHALL NOT use placeholder text as the only label.
10. THE Scenario_Builder SHALL contain no field, label, placeholder or hint that asks for an OTP, PIN, password, CVV, raw account number, raw UPI id or raw phone number, and the visible text and accessible names of its labels, placeholders and hints SHALL contain none of the words OTP, PIN, password, CVV, "account number", "UPI id" and "phone number", matched as whole words and without regard to letter case.
11. THE Scenario_Builder SHALL read the value of the amount, hours and retry count fields as follows: leading and trailing spaces are ignored; what remains is a whole number only when it is one or more of the digits 0 to 9 and no other character, so that an empty value, a sign, a decimal point, an exponent letter, a thousands separator, an inner space and any letter each make it not a whole number; leading zeros are allowed and the value is read in decimal; and the range check uses the exact decimal value, so that a string of digits above 9,007,199,254,740,991 is out of range however long it is.
12. THE Scenario_Builder SHALL word each validation message of criteria 2 and 3 so that it says in plain words that a whole number is needed, gives the lowest accepted value (1 for the amount, 0 for the hours and the retry count), and contains none of the Avoid_Words.

WHEN the Risk_Engine scores a valid evaluation whose History_Snapshot is empty and whose payment names no Beneficiary, THE Risk_Engine SHALL return a Risk_Score equal to the Baseline_Points and the same Initial_State as the Risk_Engine returned for the same Signals before this feature (`behavioral-risk-engine` Requirements 2 and 3), for every evaluation time and every Beneficiary_Ref. 5. THE Risk_Engine SHALL return the same Risk_Score and the same Contributions, in the same order, for the same Signals, the same History_Snapshot (the same History_Events in the same order), the same evaluation time and the same recipient data, and SHALL depend on no other input, including the clock, randomness, the Beneficiary_Id value and state kept from earlier calls.

8. WHEN the Risk_Engine scores a valid evaluation whose Baseline_Points are 0, THE Risk_Engine SHALL return a Risk_Score of at most 35 and the Initial_State INSTANT_PASS for every History_Snapshot and every recipient, which also keeps the pass guarantee of `behavioral-risk-engine` Requirement 4 criterion 2 for every History_Snapshot, because the inputs of that criterion earn 0 Baseline_Points.

11. THE Risk_Engine SHALL return, for every comparison of an `amount_inr` or a History_Event amount from 1 to the largest signed 64-bit integer, 9,223,372,036,854,775,807, with a threshold, with another amount or with a multiple of an amount, including the 3-times and 10-times comparisons of Requirement 11 criterion 1, the result that exact integer arithmetic with no size limit gives.

### Requirement 10: Velocity, Daily Frequency and Repeat Attempts

**User Story:** As a payer, I want RukPay to notice payments that come in quick succession or repeat to one recipient, so that a rushed or coached sequence gets a calmer look.

#### Acceptance Criteria

1. THE Risk_Engine SHALL award `velocity` points from the count of History_Snapshot events Within_Window of the Velocity_Window, whatever their amount or Beneficiary_Ref: 0 points for 0 to 2 events, 5 points for 3 or 4, 10 points for 5 to 7 and 15 points for 8 or more. An event exactly 600 seconds before the evaluation time SHALL NOT be counted, and an event 599 seconds before it SHALL be counted.
2. THE Risk_Engine SHALL award `daily_frequency` points from the count of History_Snapshot events Within_Window of the Frequency_Window, whatever their amount or Beneficiary_Ref: 0 points for 0 to 9 events, 5 points for 10 to 19 and 10 points for 20 or more. An event exactly 86,400 seconds before the evaluation time SHALL NOT be counted, and an event 86,399 seconds before it SHALL be counted.
3. WHEN the payment has a non-empty Beneficiary_Ref, THE Risk_Engine SHALL award `repeat_attempts` points from the count of History_Snapshot events Within_Window of the Repeat_Window whose Beneficiary_Ref is exactly equal text to the Beneficiary_Ref of the payment, with no case folding or trimming and whatever their amount: 0 points for 0 or 1 event, 5 points for 2 or 3 and 10 points for 4 or more. An event exactly 3,600 seconds before the evaluation time SHALL NOT be counted, and an event 3,599 seconds before it SHALL be counted.
4. WHEN the payment has an empty Beneficiary_Ref, THE Risk_Engine SHALL award 0 `repeat_attempts` points for every History_Snapshot, including a History_Snapshot whose events also have an empty Beneficiary_Ref, so that empty Beneficiary_Refs are never matched to each other.
5. THE Risk_Engine SHALL compute every count of this requirement only from the events of the History_Snapshot, which holds only History_Events recorded before the current evaluation, so that the payment being evaluated adds 0 to every count.
6. THE Risk_Engine SHALL derive each of the `velocity`, `daily_frequency` and `repeat_attempts` points from its own count only, as defined in criteria 1 to 3, and SHALL award no fewer points for a larger count than for a smaller count of the same signal, whatever the other counts and inputs are.
7. THE Risk_Engine SHALL award the `rapid_retries` points from the client-sent `rapid_retry_count` alone, by the tier rules of `behavioral-risk-engine` Requirement 2, so that the same `rapid_retry_count` gives the same `rapid_retries` points for every History_Snapshot.
8. WHEN the `velocity`, `daily_frequency` or `repeat_attempts` points are more than 0, THE Risk_Engine SHALL return one Contribution for that Signal_Id whose `points` equal the tier points of criteria 1 to 3, before the Behaviour_Cap is applied, and SHALL leave the cap to the `behaviour_cap` Contribution of Requirement 1 criterion 5.

### Requirement 11: Amount Deviation and the Pattern Table

**User Story:** As a payer, I want RukPay to notice a payment far above my recent payments and a known scam sequence, so that a sudden large transfer gets extra care.

#### Acceptance Criteria

1. WHEN the Risk_Engine scores a valid evaluation in which the History_Snapshot holds at least 5 events and `amount_inr` is at least 2000, THE Risk_Engine SHALL compare `amount_inr` with the largest amount among all events of the History_Snapshot, whatever their Beneficiary_Ref, and SHALL award `amount_deviation` points of 10 when `amount_inr` is at least 3 times and less than 10 times that largest amount, 15 when it is at least 10 times that largest amount, and 0 when it is less than 3 times that largest amount, using the comparison without integer overflow that Requirement 9 criterion 11 requires (for example, with a largest amount of 1000, an `amount_inr` of 2999 earns 0 points, 3000 and 9999 earn 10 points, and 10000 earns 15 points).
2. WHEN the Risk_Engine scores a valid evaluation in which the History_Snapshot holds fewer than 5 events, including an empty History_Snapshot, or `amount_inr` is below 2000, THE Risk_Engine SHALL award 0 `amount_deviation` points and SHALL return no `amount_deviation` Contribution.
3. THE Risk_Engine SHALL hold each Fraud_Pattern as data in the Pattern_Table, with an `id` that is unique within the table and written in lowercase snake-case, and SHALL apply every entry of that shape, in table order, using the window, minimum count, amounts and points of that entry, so that an entry added to the Pattern_Table is scored under the Signal_Id `pattern_<pattern id>` without a change to scoring code.
4. THE Pattern_Table SHALL contain the entry `test_then_large` with a window of 3600 seconds, a minimum of 3 small payments, a small-payment maximum of 1000 rupees, a large-payment minimum of 10000 rupees, 15 points and a `reason` that meets Requirement 3.
5. WHEN the Risk_Engine scores a valid evaluation in which the payment has a non-empty Beneficiary_Ref, the History_Snapshot holds at least the minimum count of small payments of a Fraud_Pattern in events whose Beneficiary_Ref equals that of the payment, which are Within_Window of the pattern window and whose amounts are each at most the small-payment maximum, and `amount_inr` is at least the large-payment minimum of that Fraud_Pattern, THE Risk_Engine SHALL award the points of that Fraud_Pattern under the Signal_Id `pattern_<pattern id>`, which is `pattern_test_then_large` for the entry `test_then_large`, counting only events that meet all three of these conditions, so that other events of the History_Snapshot neither count toward the minimum nor cancel the award (for example, three payments of 1000 rupees to one recipient, each less than 3600 seconds old, followed by a payment of 10000 rupees to that recipient earn 15 points, because an amount equal to the small-payment maximum or to the large-payment minimum meets its condition).
6. THE Risk_Engine SHALL award each Fraud_Pattern at most once per evaluation, with the points of its entry and not a multiple of them however many events qualify, and SHALL return at most one Contribution for each Fraud_Pattern.
7. THE Risk_Engine SHALL sum the `amount_deviation` points, the points of every awarded Fraud_Pattern, and the `velocity`, `daily_frequency` and `repeat_attempts` points, leaving the Baseline_Points and the Care_Points out of that sum, and SHALL apply the Behaviour_Cap to that sum once, so that the Behaviour_Points are the smaller of the sum and 25 (for example, 15 `velocity` points and 15 `amount_deviation` points give 25 Behaviour_Points and a `behaviour_cap` Contribution of -5 under Requirement 1 criterion 5).
8. WHEN the Risk_Engine scores a valid evaluation in which the payment has an empty Beneficiary_Ref, or the History_Snapshot holds fewer events meeting the three conditions of criterion 5 than the minimum count of small payments of a Fraud_Pattern, or `amount_inr` is below the large-payment minimum of that Fraud_Pattern, THE Risk_Engine SHALL award 0 points for that Fraud_Pattern and SHALL return no Contribution for it.

11. IF the Beneficiary named through `beneficiary_id` cannot be read because of a store error, THEN THE Vault_Service SHALL take the Beneficiary_Ref from the first non-empty value among `beneficiary_masked`, `upi_masked` and `phone_masked`, checked in that order, or leave it empty when all three are absent or empty, and SHALL continue the evaluation.

### Requirement 13: History Storage

**User Story:** As a cloud engineer, I want history stored in the existing table with the existing guarantees, so that both adapters behave the same.

#### Acceptance Criteria

1. THE `store` package SHALL leave the three methods of VaultStore unchanged.

THE DynamoDBStore SHALL keep each History_Event as an item of the existing table `RukPayVaults`, under a partition key derived from the Payer_Key, with a sort key that orders the events of that partition by ascending numeric event time and then by ascending event id, and with `expires_at` as the TTL attribute. THE partition key of a History_Event SHALL differ from the partition key of every Vault_Record, so that a VaultStore read never returns a History_Event and a History_Event read never returns a Vault_Record.
4. THE DynamoDBStore SHALL write each History_Event as its own item, keyed by event time and event id, so that History_Events with different event ids never share a key even when their times are equal, and concurrent writes cannot overwrite one another.
5. WHEN a read of recent History_Events is called with a limit of 1 or more, THE DynamoDBStore SHALL serve it with exactly one Query request on the partition of the requested Payer_Key, SHALL send no Scan request, and SHALL name no secondary index in that request.
6. WHERE the DynamoDBStore names a secondary index in any request, THE file `infra/dynamodb-table.json` SHALL define an index of that name whose key attributes are the ones that request uses.
7. WHEN a read finds a History_Event whose `expires_at` is non-zero and earlier than the current time of the store's clock, THE MemoryStore and THE DynamoDBStore SHALL leave it out of the result, even when DynamoDB TTL has not yet deleted the item. An `expires_at` equal to the current time SHALL not count as expired, and an `expires_at` of 0 SHALL never expire.
8. THE store contract tests SHALL run the same behavioural tests against the MemoryStore and against the DynamoDBStore backed by the Fake_DynamoDB_Client, covering criteria 7 and 9 to 13 of this requirement. THE tests SHALL include a write-then-read round trip that returns each History_Event equal to the one written in the event id, time, `amount_inr`, Beneficiary_Ref and `expires_at`, with an empty Beneficiary_Ref and an `amount_inr` of 9223372036854775807 among the cases. THE tests SHALL also include 50 writes made at the same time with different event ids, some with equal times, after which a read with a limit of 100 returns all 50.
9. IF a History_Event holds a non-empty Beneficiary_Ref that matches none of the account, phone and UPI formats checked by `store.ValidateMasked`, THEN THE MemoryStore and THE DynamoDBStore SHALL return `ErrUnmaskedIdentifier`, SHALL write nothing (the DynamoDBStore sending no write request), and SHALL keep the identifier out of the error text. THE stores SHALL accept an empty Beneficiary_Ref, SHALL check no other History_Event field, and SHALL keep every other field as given.
10. THE Fake_DynamoDB_Client SHALL support each DynamoDB operation that the DynamoDBStore newly uses for History_Events, including the write of a History_Event item, the Query request of criterion 5 and the failure injection that it offers for its existing operations. THE Fake_DynamoDB_Client SHALL stop with an error that names the unsupported part of the request, and SHALL change no stored item, on any request shape it does not know.
11. WHEN a read of recent History_Events is called with a Payer_Key and a limit, THE MemoryStore and THE DynamoDBStore SHALL return only the unexpired History_Events written under that Payer_Key. The result SHALL be the at most `limit` events with the greatest time, ties broken by the greatest event id, ordered by ascending time and then by ascending event id. THE stores SHALL return an empty list and no error when the Payer_Key has no unexpired events or when the limit is below 1, and the DynamoDBStore SHALL send no request for a limit below 1.
12. IF a write holds the same Payer_Key, event time and event id as a stored History_Event, THEN THE MemoryStore and THE DynamoDBStore SHALL return `ErrAlreadyExists` and SHALL leave the stored History_Event unchanged.
13. IF an operation of the new interface cannot complete because the context is already cancelled, because the DynamoDB client returns an error, or because a stored item cannot be decoded, THEN THE MemoryStore and THE DynamoDBStore SHALL return a non-nil error, SHALL return no History_Events from a read, SHALL leave every stored History_Event unchanged, and SHALL keep every History_Event field value out of the error text. For a cancelled context, THE stores SHALL return an error that matches the context's own error under `errors.Is` and THE DynamoDBStore SHALL send no request.

### Part D: Trusted beneficiary management (#5)

### Requirement 14: Beneficiary Record and Rules

**User Story:** As a payer, I want to keep a list of recipients with plain labels, so that I can pick them again without typing bank details.

#### Acceptance Criteria

1. THE Vault_Service SHALL store each Beneficiary of the Demo_Payer with a Beneficiary_Id, a label, one Masked_Identifier, an added time in epoch seconds, an optional verified time, a Trust_Level, a Protection_Level, a Pressure_Flag, a version, a payment count, an optional first payment amount, History_Entries and `expires_at`.
2. WHEN a Beneficiary is added, THE Vault_Service SHALL assign a new Beneficiary_Id that no stored Beneficiary of the Demo_Payer has, set the Trust_Level to `NEW`, set the Protection_Level to `EXTRA_CARE`, set the added time to the current time in epoch seconds, set no verified time, set the version to 1, set the payment count to 0 and set no first payment amount.
3. THE Vault_Service SHALL accept a label only when, after trimming leading and trailing white-space characters, it holds 1 to 40 Unicode characters, has no run of more than 4 consecutive decimal digits (`0` to `9`), has no `@` character, and `redact.Text` returns it unchanged, and SHALL store the trimmed label. A label of 40 characters and a label with a run of 4 digits are accepted. An empty label after trimming, a label of 41 characters and a label with a run of 5 digits are refused.
4. THE Vault_Service SHALL accept one Masked_Identifier only when the whole value, without trimming, matches the account format `XXXX-XXXX-4821`, the phone format `+91-XXXXXX3210` or the UPI format `r***@okaxis`, checked with the same patterns as `store.ValidateMasked`, and SHALL refuse an empty identifier.

IF an add request leaves out `label` or `identifier_masked` or holds either outside these rules, or a PATCH request holds a `label` outside these rules, THEN THE Router SHALL respond with HTTP 400 and the code `invalid_field`, naming `label` or `identifier_masked` in the error `field` (`label` when both are at fault), and SHALL store nothing and change nothing.
6. IF a valid add request holds a Masked_Identifier that is equal, by exact case-sensitive match whatever the label, to the Masked_Identifier of an unexpired Beneficiary of the Demo_Payer, THEN THE Router SHALL respond with HTTP 409 and the code `duplicate_beneficiary` and SHALL store nothing.
7. IF the Demo_Payer already has 50 unexpired Beneficiaries when a valid add request that is not a duplicate arrives, THEN THE Router SHALL respond with HTTP 409 and the code `beneficiary_limit` and SHALL store nothing.
8. WHEN a Beneficiary is added, THE Vault_Service SHALL set the Pressure_Flag to true if the add request is in a Pressure_Context and to false if it is not.
9. THE Vault_Service SHALL store no raw account number, raw UPI id, raw phone number, OTP, PIN or password in any Beneficiary_Record, including its label and its History_Entries, and SHALL drop every request field that Requirement 15 does not name for that route.
10. IF the store cannot read the Beneficiaries of the Demo_Payer or cannot write the new Beneficiary_Record while an add request is handled, THEN THE Router SHALL respond with HTTP 500 and the code `internal` with a fixed calm message, SHALL leave the stored Beneficiaries as they were before the request, and SHALL NOT return a Beneficiary_View.

WHEN `GET /api/v1/beneficiaries` is called, THE Router SHALL respond with HTTP 200 and a JSON list of the Beneficiary_Views of the Demo_Payer, each without its history, ordered by added time with the earliest first and then by Beneficiary_Id in ascending order, and SHALL respond with an empty list when the Demo_Payer has no Beneficiary.

IF a PATCH holds none of `label`, `trust_level` and `protection_level`, or holds a `label` outside Requirement 14 criterion 3, a `trust_level` other than `NEW` or `TRUSTED`, or a `protection_level` other than `EXTRA_CARE` or `STANDARD` (compared exactly, including letter case, with a field that is absent or JSON null counting as not held), THEN THE Router SHALL respond with HTTP 400 and SHALL change nothing, using the code `invalid_field` with the first offending field in the order of criterion 5 named in the error `field` when a value is at fault, and the code `invalid_request` when none of the three fields is held.

WHEN `DELETE /api/v1/beneficiaries/{id}` is called for a stored Beneficiary, THE Router SHALL remove the Beneficiary and its History_Entries, respond with HTTP 200 and a JSON object that holds no label, Masked_Identifier or History_Entry, and answer every later request for that id with HTTP 404 and the code `not_found`.
9. IF the id in the path of a Beneficiary route is not stored, including an id that is not 32 lowercase hexadecimal characters and a Beneficiary_Record that has expired, THEN THE Router SHALL respond with HTTP 404 and the code `not_found`, with a body that holds no submitted value, and SHALL change nothing.
10. IF two requests among PATCH, DELETE and verification for the same Beneficiary read the same version of its Beneficiary_Record before either one writes, THEN THE Vault_Service SHALL apply exactly one of them without retrying the other and respond to the other with HTTP 409, the code `state_conflict` and the current Beneficiary_View without its history, or with HTTP 404 and the code `not_found` when the applied request was a DELETE.

THE Router SHALL use the shared error body `{ "error": { "code", "message", "field" } }` for every error response of the Beneficiary routes, with `field` present only when one request field is at fault, and SHALL give each new error code (`duplicate_beneficiary`, `beneficiary_limit` and `not_ready`) a calm message that is the same text on every response with that code (with `not_ready` using one fixed text for each of its three causes), that holds none of the Avoid_Words and that holds no submitted value.

THE Router SHALL write log lines for the Beneficiary routes that hold the method, the route pattern with the `{id}` placeholder instead of the requested path, and the status only, and SHALL NOT write a Beneficiary_Id, label, identifier, request body, history or any 32-character hexadecimal id taken from the request, on success and on every error path.

15. IF the body of one of the three routes in criterion 14 is empty, is not valid JSON, is not a single JSON object, holds content after that object, or holds a field of that route with the wrong JSON type, THEN THE Router SHALL respond with HTTP 400 and the code `invalid_request` and SHALL store and change nothing.

IF a request to a Beneficiary route fails more than one check, THEN THE Router SHALL respond for the first failed check in this order: body size (criterion 14), body shape (criterion 15), field values (criterion 7 and Requirement 14 criterion 5), id not stored (criterion 9), then refusals and conflicts with HTTP 409.

### Requirement 16: Trust Lifecycle and Protection Level

**User Story:** As a payer, I want trust to be earned slowly, so that a scammer cannot talk me into trusting a new contact in one call.

#### Acceptance Criteria

1. WHEN a PATCH asks for `trust_level` `TRUSTED`, THE Vault_Service SHALL grant it, by setting the Trust_Level to `TRUSTED`, only when the Beneficiary has a verified time, the current time is at or after the added time plus the Trust_Waiting_Period, and the request is not in a Pressure_Context, comparing times in whole epoch seconds.
2. IF a PATCH asks for `TRUSTED` and the Beneficiary has no verified time, THEN THE Router SHALL respond with HTTP 409, the code `not_ready` and the field `trust_level`, and SHALL change nothing, including any other change asked for in the same PATCH.
3. IF a PATCH asks for `TRUSTED` and the current time is earlier, by 1 second or more, than the added time plus the Trust_Waiting_Period (259,200 seconds, or 604,800 seconds when the Pressure_Flag is set at the time of the request), THEN THE Router SHALL respond with HTTP 409, the code `not_ready` and the field `trust_level`, and SHALL change nothing, including any other change asked for in the same PATCH.
4. IF a PATCH asks for `TRUSTED` or for `protection_level` `STANDARD` in a Pressure_Context, THEN THE Router SHALL respond with HTTP 409, the code `not_ready` and, in `field`, the refused property (`trust_level` for `TRUSTED`, `protection_level` for `STANDARD`), and SHALL change nothing, including any other change asked for in the same PATCH.
5. WHEN THE Router responds with `not_ready`, THE Vault_Service SHALL supply a fixed calm message for the cause, using a different message for each of the three causes of criteria 2, 3 and 4, where a calm message is one sentence of 1 to 160 characters, identical on every response for that cause, with no Avoid_Word and no label, identifier or submitted value.
6. WHEN a PATCH changes the Trust_Level of a Beneficiary from `NEW` to `TRUSTED`, THE Vault_Service SHALL set its Protection_Level to `STANDARD` in the same write, unless the same PATCH asks for `protection_level` `EXTRA_CARE`.
7. WHEN a PATCH asks for `trust_level` `NEW`, THE Vault_Service SHALL set the Trust_Level to `NEW` and the Protection_Level to `EXTRA_CARE`, with no waiting and in any context, including when the Trust_Level is already `NEW`, and SHALL leave the added time, the verified time and the Pressure_Flag unchanged.
8. WHEN a PATCH asks for `protection_level` `EXTRA_CARE`, THE Vault_Service SHALL set the Protection_Level to `EXTRA_CARE` for a Beneficiary of either Trust_Level, with no waiting, no verified time needed and in any context, and SHALL leave the Trust_Level as the same PATCH leaves it.
9. IF a PATCH asks for `protection_level` `STANDARD` for a Beneficiary whose Trust_Level, after the `trust_level` change in the same PATCH if there is one, is `NEW`, THEN THE Router SHALL respond with HTTP 409, the code `not_ready` and the field `protection_level`, with a fixed calm message that differs from the three messages of criterion 5, and SHALL change nothing, including any other change asked for in the same PATCH.
10. THE Vault_Service SHALL keep the invariants that `STANDARD` implies `TRUSTED`, and that `TRUSTED` implies a verified time, in every stored Beneficiary_Record and every returned Beneficiary_View, after every operation of Requirements 14 to 18 (add, PATCH whether applied or refused, verification and payment) and after a request that loses a race, for every sequence of those operations.
11. WHEN a PATCH holds `label`, THE Vault_Service SHALL set the label to the new value that meets Requirement 14 criterion 3, in any context, and the label change by itself SHALL leave the Trust_Level, Protection_Level, Pressure_Flag, added time and verified time of the Beneficiary unchanged.
12. THE Vault_Service SHALL evaluate the Trust_Waiting_Period when the request arrives, from the stored added time, the stored Pressure_Flag and the clock reading of that request, with no background timer or scheduled job, and SHALL keep a `NEW` Beneficiary at `NEW` after the Trust_Waiting_Period has passed until a PATCH grants `TRUSTED`.
13. THE Vault_Service SHALL take the current time for each PATCH from the injectable clock of `cooling-off-vault` Requirement 4 criterion 7, read once per PATCH, and SHALL use that one reading for the Trust_Waiting_Period comparison and for every time it writes in that PATCH.
14. WHEN a PATCH holds `is_late_night` as `true` or `active_unknown_call` as `true`, THE Vault_Service SHALL treat the PATCH as in a Pressure_Context, and SHALL treat a PATCH in which both fields are `false` or omitted as not in a Pressure_Context.
15. IF a PATCH holds `is_late_night` or `active_unknown_call` with a value other than the JSON values `true` and `false`, THEN THE Router SHALL respond with HTTP 400, the code `invalid_field` and the name of that property in `field`, and SHALL change nothing.
16. IF a PATCH is refused for more than one cause, THEN THE Router SHALL respond with the first of these, in this order: the HTTP 400 of Requirement 15 criterion 7 or of criterion 15 of this requirement; `not_ready` for `TRUSTED` without a verified time (criterion 2); `not_ready` for `TRUSTED` before the Trust_Waiting_Period has passed (criterion 3); `not_ready` for `TRUSTED` or `STANDARD` in a Pressure_Context (criterion 4); `not_ready` for `STANDARD` on a Beneficiary whose resulting Trust_Level is `NEW` (criterion 9), using the message and `field` of that cause.

### Requirement 17: Beneficiary Verification

**User Story:** As a payer, I want three calm questions when I add a new recipient, so that I stop and think before I trust someone who may be a scammer's account.

#### Acceptance Criteria

1. WHEN `POST /api/v1/beneficiaries/{id}/verification` receives, for a stored Beneficiary, a JSON body whose `answers` object holds `coercion`, `acquaintance` and `secrecy`, each exactly the upper-case string `YES` or `NO`, THE Vault_Service SHALL classify the three answers as `PASSED` or `NOT_PASSED` under criteria 2 and 3 and SHALL ignore any other key of the body.
2. WHEN `coercion` is `NO`, `acquaintance` is `YES` and `secrecy` is `NO`, THE Vault_Service SHALL set the verified time to the current time, append one history entry of kind `VERIFIED` whose `at` is that same time, leave the Trust_Level, the Protection_Level and the Pressure_Flag unchanged, and respond with HTTP 200, outcome `PASSED` and the updated Beneficiary_View, whose `verified_at` is that same time.
3. WHEN at least one of these holds, namely `coercion` is `YES`, `acquaintance` is `NO` or `secrecy` is `YES`, THE Vault_Service SHALL set the Pressure_Flag, set the Trust_Level to `NEW`, set the Protection_Level to `EXTRA_CARE`, append one history entry of kind `VERIFICATION_NOT_PASSED` whose `at` is the current time, leave the verified time unchanged, and respond with HTTP 200, outcome `NOT_PASSED`, one fixed calm message and the updated Beneficiary_View. The fixed calm message SHALL be the same text for all seven answer combinations that lead to `NOT_PASSED`, SHALL be 1 to 200 characters long, SHALL contain no Avoid_Words, and SHALL not say which answer led to it.
4. IF `answers` is absent or is not a JSON object, or any of `coercion`, `acquaintance` and `secrecy` is absent, or any of them holds anything other than the exact strings `YES` or `NO` (including `yes`, `true`, `null`, an empty string and a string with spaces around it), THEN THE Router SHALL respond with HTTP 400 and the shared error body of Requirement 15 criterion 11, with `field` set to `answers` when the object is absent or not an object and otherwise to the first offending answer in the order `coercion`, `acquaintance`, `secrecy`, and SHALL change nothing, append no history entry and store no submitted value.
5. THE Vault_Service SHALL store, log and return only the outcome of a verification and no answer, so that two requests that give different answers with the same outcome, from equal Beneficiary_Records at the same current time, leave equal Beneficiary_Records.
6. WHEN a verification request names a Beneficiary that already has a verified time, THE Vault_Service SHALL process it under criteria 1 to 5 in the same way as for a Beneficiary with no verified time, so that a `PASSED` outcome replaces the verified time with the current time and appends a further `VERIFIED` history entry.
7. THE Beneficiary_Manager SHALL ask the three questions one at a time, each with a "Yes" button and a "No" button of at least 48 by 48 pixels with at least 12 pixels between them, question text of at least 18 pixels, a progress line that reads "Question 1 of 3", "Question 2 of 3" or "Question 3 of 3" for the question on screen, and a "Back" control that returns to the previous question, keeps the answers already given and is disabled on question 1, with no countdown and no message that disappears by itself, in the calm style of the Reality_Check_Modal.
8. THE Beneficiary_Manager SHALL word the questions, in this order for the answers `coercion`, `acquaintance` and `secrecy`, as: "Did someone on a phone or video call ask you to add this person?", "Do you know this person, and have you spoken to them on a number you already had?" and "Did anyone ask you to keep this person a secret from your family or bank?"
9. WHILE the Beneficiary verification dialog is open, THE Beneficiary_Manager SHALL keep keyboard focus inside the dialog, so that Tab and Shift+Tab never reach the page behind it, SHALL move focus to the first answer button each time a question is shown, including after "Back", and SHALL announce itself with `role="dialog"`, `aria-modal="true"` and an accessible title equal to the visible heading text.
10. THE Vault_Service SHALL apply all changes of one verification in one conditional write on the version it read, SHALL read the current time once from the injectable clock of Requirement 16 criterion 13 and use that value for the verified time and for the `at` of the history entry, and SHALL change no field other than those that criterion 2 or 3 names, the version and `expires_at`, so that a request answered with `state_conflict` under Requirement 15 criterion 10 changes nothing and appends no history entry.
11. IF the Beneficiary cannot be read, or the write fails for a reason other than a version conflict, THEN THE Router SHALL respond with HTTP 500 and the shared error body with a fixed calm message that holds no store error text and no submitted value, and SHALL change nothing.
12. WHEN the user answers the third question, THE Beneficiary_Manager SHALL send one verification request holding the three recorded answers, with "Yes" recorded as `YES` and "No" recorded as `NO` for every question including the second, where `YES` is the answer that can pass, and, once the response arrives, SHALL close the dialog and, for outcome `NOT_PASSED`, show the `message` of the response beside that Beneficiary until the user acts or the list changes.

### Requirement 18: Payments That Name a Beneficiary

**User Story:** As a payer, I want a payment to a saved recipient to use that recipient's age and trust, so that new recipients get extra care and old trusted ones do not.

#### Acceptance Criteria

1. WHEN an evaluate request holds a `beneficiary_id` of a stored Beneficiary and omits `beneficiary_age_hours` (the key is absent or its value is null), THE Vault_Service SHALL use as the `beneficiary_age_hours` Signal the whole hours from the added time to the current time, rounded down, and 0 when the current time is earlier than the added time. The current time comes from the injectable clock of Requirement 16 criterion 13.
2. WHEN an evaluate request holds both a `beneficiary_id` of a stored Beneficiary and a `beneficiary_age_hours` value (including 0), THE Vault_Service SHALL use the smaller of the two ages in whole hours as the `beneficiary_age_hours` Signal.
3. WHEN an evaluate request holds no `beneficiary_id` (the key is absent or its value is null), THE Vault_Service SHALL read no Beneficiary_Record and SHALL treat `beneficiary_age_hours` and the masked identifier fields exactly as before this feature, so that an omitted `beneficiary_age_hours` counts as 0.
4. WHEN an evaluate request holds a `beneficiary_id` of a stored Beneficiary, THE Vault_Service SHALL take the recipient Masked_Identifier from the Beneficiary_Record, SHALL use it as the Beneficiary_Ref, and SHALL store it in the Vault_Record field that matches its format (`beneficiary_masked` for the account format, `upi_masked` for the UPI format, `phone_masked` for the phone format). THE Vault_Service SHALL ignore the values of `beneficiary_masked`, `upi_masked` and `phone_masked` in that request, so that they change no score, no Beneficiary_Ref and no stored or returned recipient identifier. A value among them that fails the identifier check of `cooling-off-vault` Requirement 1 criterion 7 is still rejected under that criterion.
5. IF an evaluate request holds a `beneficiary_id` that is not 32 lowercase hexadecimal characters (an empty string included), or that names no stored Beneficiary (no Beneficiary_Record of the Demo_Payer exists for it, or the record has expired), THEN THE Router SHALL respond with HTTP 400, the code `invalid_field` and the field `beneficiary_id`, with the same fixed calm message for both causes and no submitted value in the body, and SHALL create no vault, record no History_Event and write no `PAYMENT` history entry.
6. WHEN a payment names no Beneficiary, or names a Beneficiary on `STANDARD` protection, THE Risk_Engine SHALL award Care_Points of 0.
7. WHEN a payment names a Beneficiary on `EXTRA_CARE` protection, THE Risk_Engine SHALL award Care_Points of 10 if the Beneficiary has no verified time or has the Pressure_Flag, and Care_Points of 5 if the Beneficiary has a verified time and no Pressure_Flag.
8. WHEN the Risk_Engine awards Care_Points above 0, THE Risk_Engine SHALL add one Contribution with the Signal_Id `beneficiary_care`, with `points` equal to the Care_Points, and with a `reason` that is the fixed sentence for that tier under Requirement 3 criterion 1 and says the recipient is new or on the extra-care list.
9. THE Risk_Engine SHALL award Care_Points only as additions, so that the Baseline_Points depend on the five Signals alone and, with every other input equal, changing a Beneficiary from `EXTRA_CARE` to `STANDARD` protection lowers the Risk_Score by at most 10 points and never below the Baseline_Points.
10. IF the Beneficiary_Record of a stored Beneficiary cannot be read because of a store error other than "not found", THEN THE Vault_Service SHALL score the payment from the explicit request values (`beneficiary_age_hours` and the masked identifier fields, treated as before this feature) with 0 Care_Points, SHALL create the vault, SHALL return no error for the failed read, and SHALL write no `PAYMENT` history entry.
11. WHEN a payment names a stored Beneficiary whose Beneficiary_Record was read and a vault is created, in any Initial_State, THE Vault_Service SHALL add a `PAYMENT` history entry to the Beneficiary_Record with `at` equal to the evaluation time in epoch seconds and `amount_inr` equal to the request amount, within the 50-entry limit of Requirement 19 criterion 2.
12. IF the `PAYMENT` history entry cannot be written, whether from a store error, a version conflict, or a Beneficiary_Record that was removed or expired after it was read, THEN THE Vault_Service SHALL return the same Risk_Score, state and Explanation that it would return after a successful write, SHALL keep the vault it created, SHALL leave the Beneficiary_Record unchanged, and SHALL NOT retry the write.
13. WHEN the `PAYMENT` history entry is written, THE Vault_Service SHALL in the same write increase the payment count of the Beneficiary_Record by 1, and SHALL set the first payment amount to `amount_inr` only when the payment count was 0 before this payment, leaving the first payment amount unchanged otherwise.

### Requirement 19: Beneficiary History and Risk Indicators

**User Story:** As a payer, I want to see what has happened with a recipient and why RukPay is careful with it, so that I can decide whether to trust it.

#### Acceptance Criteria

1. WHEN one of the events below happens to a Beneficiary, THE Vault_Service SHALL append one History_Entry whose `at` is the current time in epoch seconds and whose `kind` is the code of that event, in the same write of the Beneficiary_Record that applies the change, or, for `PAYMENT`, that records the payment. The events are `ADDED` when the Beneficiary is added, `VERIFIED` each time a Beneficiary_Verification has the outcome `PASSED`, `VERIFICATION_NOT_PASSED` each time a Beneficiary_Verification has the outcome `NOT_PASSED`, `TRUSTED` when the stored Trust_Level changes from `NEW` to `TRUSTED`, `TRUST_REMOVED` when it changes from `TRUSTED` to `NEW`, `PROTECTION_RAISED` when the stored Protection_Level changes from `STANDARD` to `EXTRA_CARE`, `PROTECTION_LOWERED` when it changes from `EXTRA_CARE` to `STANDARD`, `RENAMED` when the stored label changes to a different value, and `PAYMENT` when a payment that names the Beneficiary creates a vault. A request that leaves a stored value unchanged SHALL append no entry for that value, and a request that causes several events SHALL append their entries in the order in which the codes are listed in this criterion.
2. THE Vault_Service SHALL keep at most the 50 most recently appended History_Entries of a Beneficiary, discarding the earliest appended entry first when a 51st entry is appended, and SHALL return them newest first, meaning in reverse order of appending, whenever the history of a Beneficiary is returned (Requirement 15 criterion 4).
3. ### Requirement 20: Beneficiary Storage

**User Story:** As a cloud engineer, I want recipients stored in the existing table with race-free updates and automatic cleanup, so that the demo stays small and safe.

#### Acceptance Criteria

1. THE Store SHALL define a new interface for Beneficiary_Records, separate from VaultStore, with five operations (create, get by Beneficiary_Id, list for the Demo_Payer in ascending Beneficiary_Id order, conditional replace and delete), THE MemoryStore and THE DynamoDBStore SHALL each implement it, and THE Store SHALL leave the three methods of VaultStore unchanged.
2. THE DynamoDBStore SHALL keep each Beneficiary_Record, with its History_Entries, as one item of the existing table `RukPayVaults` under a partition key derived from the Payer_Key and a sort key that holds the Beneficiary_Id, and the partition key value SHALL differ from the one used for History_Events and from every vault item key, so that one query on that partition, with no secondary index, lists every Beneficiary_Record of the Demo_Payer and no other item.
3. WHEN a conditional replace names a stored Beneficiary_Id whose record has not expired, together with the version the caller read, THE stores SHALL replace the record in one atomic operation only if the stored version equals that version, SHALL store the new record with a version of that version plus 1 whatever version the new record carries, and SHALL otherwise return a condition-failed error and leave the stored record unchanged.
4. THE stores SHALL set the `expires_at` of a Beneficiary_Record, in epoch seconds, to the time of its latest write plus 2,592,000 seconds (30 days), where a write is a create or a successful replace, and SHALL leave a Beneficiary_Record whose `expires_at` is earlier than the current time out of every get and list, even when DynamoDB has not yet deleted its item.
5. WHEN a valid Beneficiary_Record (one whose identifier is in a Masked_Identifier format), with 0 to 50 History_Entries, is created or replaced and then read by get or list before its `expires_at`, THE stores SHALL return a Beneficiary_Record equal field for field to the one written, with the History_Entries in the written order and an absent verified time still absent, except for the `expires_at` set by criterion 4 and, after a replace, the version set by criterion 3.
6. IF a create or a conditional replace holds a Beneficiary_Record whose identifier is empty or is not in a Masked_Identifier format (the account, phone or UPI format of Requirement 14.4), THEN THE stores SHALL return `ErrUnmaskedIdentifier` before any other check, SHALL write nothing and SHALL leave any stored record unchanged.
7. THE stores SHALL build every error that they return for a Beneficiary operation, including an error that wraps a DynamoDB client failure, so that its text and every wrapped error hold only the operation name, the Beneficiary_Id when the operation names one, and a fixed description, with no label, identifier, amount, History_Entry or request content, and so that the error stays identifiable as its kind (already-exists, not-found, condition-failed or unmasked-identifier).
8. THE store contract tests SHALL run the same behavioural tests against the MemoryStore and against the DynamoDBStore backed by the Fake_DynamoDB_Client, SHALL cover create, duplicate (a create that names a Beneficiary_Id already stored), get, list, conditional update, delete, expiry (with a clock that the test controls) and concurrent updates, and SHALL check for every failure case the error kind and that the stored record is unchanged.
9. WHEN at least 20 goroutines call the conditional replace at the same moment on one Beneficiary_Record with the same expected version, THE stores SHALL let exactly one call succeed, SHALL return a condition-failed error to every other call, and SHALL leave the stored record equal to the one the successful call wrote, with a version of the expected version plus 1.
10. IF a create names a Beneficiary_Id that is already stored, even when that record has expired and DynamoDB has not yet deleted its item, THEN THE stores SHALL return an already-exists error and SHALL leave the stored record unchanged.
11. IF a get, a conditional replace or a delete names a Beneficiary_Id that is not stored or whose record has expired, THEN THE stores SHALL return a not-found error and SHALL change nothing.
12. WHEN a delete names a stored Beneficiary_Id whose record has not expired, THE stores SHALL remove the Beneficiary_Record together with its History_Entries, so that a later get returns a not-found error and a later list leaves it out.

### Requirement 27: Backend Automated Tests

**User Story:** As a maintainer, I want randomized and example tests on every new rule, so that no later change silently breaks a guarantee.

#### Acceptance Criteria

1. THE PBT_Suite SHALL use `pgregory.net/rapid` with at least 1000 generated cases per property, with that count set in the test code so that `go test ./...` without extra flags runs it. THE PBT_Suite SHALL pass with exit status 0 under `go test ./...` within the default 10-minute `go test` timeout of each package, using the MemoryStore, the injectable clock of `cooling-off-vault` Requirement 4 criterion 7 and no connection to a remote host. Only the store contract tests of criterion 14 also use the DynamoDBStore backed by the Fake_DynamoDB_Client.
2. THE PBT_Suite SHALL test, for every generated valid evaluation (Signals with `amount_inr` up to 9,223,372,036,854,775,807, a History_Snapshot of 0 to 100 events, an evaluation time and recipient data), three things. First, the `points` of the Contributions add up to the Risk_Score. Second, evaluating the same inputs twice gives Explanations with the same Contributions in the same order. Third, the baseline Contributions agree with an independent reference model written from the tier tables of `behavioral-risk-engine` Requirement 2. That model shares no code, table or constant with the Risk_Engine. Agreement means the same Signal_Ids in the order of Requirement 1 criterion 3, the same `points` for each, and a baseline Signal_Id absent exactly when it earns 0 points.
3. THE PBT_Suite SHALL test, with a second independent reference model, that the behavioural Contributions, the Behaviour_Points and the Care_Points equal the model's values. That model shares no code with the Risk_Engine or with the model of criterion 2, and it computes with arbitrary-precision integers. The generated histories SHALL include each of these cases:
   - every tier boundary of Requirements 10, 11 and 18:
     - `velocity` counts 2, 3, 4, 5, 7 and 8;
     - `daily_frequency` counts 9, 10, 19 and 20;
     - `repeat_attempts` counts 1, 2, 3 and 4;
     - `amount_deviation` with 4 and 5 events, with `amount_inr` of 1999 and 2000, and with `amount_inr` one below, equal to and one above 3 times and 10 times the largest amount;
     - `pattern_test_then_large` with 2 and 3 small payments, small payments of 1000 and 1001 rupees, and a large payment of 9999 and 10000 rupees;
     - Care_Points for `STANDARD` protection, for `EXTRA_CARE` with no verified time, for `EXTRA_CARE` with the Pressure_Flag, and for `EXTRA_CARE` with a verified time and no Pressure_Flag;
   - a window boundary, meaning History_Events whose age is one second less than, equal to and one second more than each of the Velocity_Window, the Frequency_Window, the Repeat_Window and the pattern window, plus an event time later than the evaluation time;
   - behavioural sums before the Behaviour_Cap that are below, equal to and above the cap;
   - the amount 9,223,372,036,854,775,807 as both `amount_inr` and a History_Event amount.
4. THE PBT_Suite SHALL test, for generated Signals, History_Snapshots and recipients, five things:
   - An empty History_Snapshot with no Beneficiary gives the Risk_Score and Initial_State of the shipped `Evaluate`, which the test holds as a frozen copy of its code from before this feature.
   - The Behaviour_Points never exceed 25 and the Care_Points never exceed 10, including cases where the points before a cap exceed that cap.
   - The Risk_Score never exceeds 100.
   - The Risk_Score is never below the Baseline_Points.
   - Baseline_Points of 75 or more give LOCKED_15M for every History_Snapshot and every recipient.
5. THE PBT_Suite SHALL test, for every generated History_Snapshot of 0 to 100 events and every generated recipient, that a payment whose Baseline_Points are 0 gives INSTANT_PASS. THE PBT_Suite SHALL also test, with no Beneficiary named and for every generated History_Snapshot, that the request body of each of the three Presets, as the Preset_Bar sends it, gives its documented state: INSTANT_PASS for the Safe Preset, REALITY_CHECK for the Medium Preset and LOCKED_15M for the High_Risk Preset.
6. THE PBT_Suite SHALL test, with the Signals, the evaluation time and the recipient data unchanged, that the `points` of `velocity`, `daily_frequency` and `repeat_attempts` never decrease when History_Events are added one at a time to a generated History_Snapshot so that the count each of them reads rises from 0 up to 100. A Contribution that is absent counts as 0 points.
7. THE PBT_Suite SHALL test that every explanation sentence, every Fraud_Pattern reason and every added summary phrase meets Requirement 3. Explanation sentences and Fraud_Pattern reasons SHALL meet criteria 2 to 6 of Requirement 3, and added summary phrases SHALL meet criterion 10 of Requirement 3. The checks are:
   - a `reason` has 1 to 20 whitespace-separated words and one terminal `.`, with no other `.`, `!` or `?`;
   - no Avoid_Word occurs in it, compared as a case-insensitive substring against a list held in the test;
   - it has no run of 5 or more digits, no `@`, no text in a Masked_Identifier format, no `₹`, no `Rs` and no `INR`;
   - `redact.Text` returns it unchanged.

   The test SHALL find the sentences by parsing the source file or files that hold them (Requirement 3 criterion 7) and checking every string constant they declare, and SHALL find the Fraud_Pattern reasons by iterating the Pattern_Table. The test SHALL fail when either scan finds no sentence, so that a sentence added later is checked without a change to the test and the check cannot pass with nothing to check.
8. THE PBT_Suite SHALL test, over generated sequences of 1 to 40 operations, that the invariants below hold after every operation.
   - The operations are add, verify, trust, change, remove and payment. Trust is a PATCH asking for `trust_level` `TRUSTED`, and change is a PATCH of `label`, of `trust_level` `NEW` or of `protection_level`. Verify uses generated `YES` and `NO` answers, and each operation has a generated Pressure_Context.
   - The clock advances between operations by a generated 0 to 700,000 seconds, with steps that land exactly on, and one second before, the end of each Trust_Waiting_Period.
   - Invariants: `STANDARD` implies `TRUSTED`; `TRUSTED` implies a verified time; at every grant of `TRUSTED` the grant time is at or after the added time plus the Trust_Waiting_Period that applied at that moment (72 hours, or 168 hours when the Pressure_Flag is set); and no operation made in a Pressure_Context changes a Beneficiary from `NEW` to `TRUSTED` or from `EXTRA_CARE` to `STANDARD`.
9. THE PBT_Suite SHALL test, for generated added times, current times and request ages `beneficiary_age_hours` from 0 to 9,223,372,036,854,775,807, that the age the Vault_Service uses to score a payment is as follows. With no `beneficiary_age_hours` sent, it is the whole hours from the added time to the current time, rounded down and never below 0. With both given, it is the smaller of the two. When the current time is before the added time, which is a clock that moved backwards, it is 0 from the added time. The generated cases SHALL include a difference of 3599, 3600 and 3601 seconds, and a request age one below, equal to and one above the age computed from the added time.
10. THE PBT_Suite SHALL test, with at least 50 goroutines released together by one start signal so that they overlap, two things. First, after N concurrent evaluations (N from 50 to 200), the store holds exactly one History_Event for each evaluation that returned success. Second, when the goroutines each apply a different change to one Beneficiary that they all read at the same version, exactly one change succeeds, every other change receives the conflict outcome (`state_conflict` with HTTP 409 at the Router, and the condition-failed error at the store), and the stored Beneficiary_Record equals the one the successful change wrote.
11. THE test suite SHALL include a JSON contract test, in the style of `vault/types_test.go`, that does five things:
    - It pins the exact key set of a Contribution (`signal`, `points`, `reason`) and of the Beneficiary_View, using the keys of Requirement 19 criterion 3 with `verified_at` present only when a verified time exists.
    - It pins the exact key set of every new request body. These are the body of `POST /api/v1/beneficiaries` (`label`, `identifier_masked`, `is_late_night`, `active_unknown_call`), the body of `PATCH /api/v1/beneficiaries/{id}` (`label`, `trust_level`, `protection_level`), the body of `POST /api/v1/beneficiaries/{id}/verification` (`answers` holding `coercion`, `acquaintance`, `secrecy`), and the `beneficiary_id` added to the evaluate body. Each optional key is omitted when it is not set.
    - It round-trips each of these types.
    - It reads the declared JSON fields of each type, so that a field added without a test change fails.
    - It proves that unknown fields such as `otp`, `pin`, `password`, `passcode`, `cvv`, `account_number`, `upi_id` and `phone` decode without error, are not kept, and appear neither as a key nor as a value when the decoded value is encoded again.
12. THE test suite SHALL include an import test with two parts. First, no non-test Go file of `backend/internal/risk` directly imports an I/O package, meaning `os`, `io`, `io/ioutil`, `io/fs`, `net`, any path under `net/`, `os/exec`, `syscall`, `database/sql`, `log`, `log/slog`, any `github.com/aws/` package, or a logging package banned in `store/imports_test.go`. Second, no Go file under `backend`, test files included, imports a path that contains `sqlite` in any letter case, and neither `go.mod` nor `go.sum` mentions `sqlite`. This second scan SHALL cover every package directory under `backend`, so that it includes every new package. The test SHALL fail when a scan finds no Go file in a directory it checks.
13. THE test suite SHALL include in-process HTTP tests of the Router, with the MemoryStore and the injectable clock, for each of the six routes of Requirement 15 criterion 1 and for the changed evaluate route. The tests SHALL cover:
    - one success case per route with the status of Requirement 15 and the keys of the response;
    - one case for each HTTP status and error code named in Requirements 14 to 18, with the three `not_ready` causes giving three different messages;
    - the shared error body shape `{ "error": { "code", "message", "field" } }`, with no submitted value, stack trace or store error text in it;
    - a CORS preflight whose methods list `PATCH` and `DELETE` with `GET`, `POST` and `OPTIONS`;

    - the log lines, where requests that carry a sentinel label, Masked_Identifier and Beneficiary_Id leave log output that holds only the method, route pattern and status and none of the sentinel values.
14. THE store test suite SHALL cover each new store with the shared contract tests of Requirements 13 and 20, run by the same test function against both the MemoryStore and the DynamoDBStore backed by the Fake_DynamoDB_Client. For the History interface, the tests SHALL cover the round trip returning each History_Event equal to the one written, exclusion of an expired History_Event, `ErrUnmaskedIdentifier` with nothing written, concurrent writes that each keep their own item, and the Fake_DynamoDB_Client stopping with a clear error on an unknown request shape.
